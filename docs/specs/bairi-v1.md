# 焙日 Bairi 第一版：精品咖啡豆網路商店

## Problem Statement

我在找全端工程師的工作，需要一份作品，讓面試官幾分鐘內就能確認兩件事：我能把購物網站的常見功能完整做出來，而且畫面看起來專業、有設計感。常見的求職作品多半只有商品列表和購物車，沒有付款、庫存、後台，也看不出開發者想過真實電商會遇到的問題，例如兩個人同時買最後一包、付款超時。作品還必須長期免費上線，面試官點開網址就能實際操作前台與後台。

## Solution

打造「焙日 Bairi」，一間販售精品咖啡豆的網路商店，採日系極簡的視覺風格。

- **顧客**可以依產地、處理法、烘焙度與風味標籤找咖啡豆，選擇規格（重量）與研磨方式加入購物車，用綠界測試環境付款，並收到訂單 Email。
- **訪客**不用登入也能使用購物車，結帳時再登入，購物車會自動合併。
- **店家**可以在獨立的後台管理咖啡豆、規格、庫存、圖片與訂單狀態。
- 網站免費部署在 Render，資料庫使用 Aiven MySQL。公開的店家測試帳號可以實際操作後台，demo 資料在網站每次從休眠醒來時重置。
- repo 附有針對關鍵業務規則的自動化測試、一支端對端購物流程測試，以及每次 push 都會執行的 CI。

## User Stories

### 瀏覽咖啡豆

1. As a 訪客, I want to 在首頁看到精選與最新的咖啡豆, so that 我第一眼就知道這間店賣什麼、風格如何
2. As a 訪客, I want to 瀏覽所有咖啡豆的列表, so that 我可以比較不同的豆子
3. As a 訪客, I want to 依產地篩選咖啡豆（可複選）, so that 我能找到喜歡的產區
4. As a 訪客, I want to 依處理法篩選咖啡豆（可複選）, so that 我能找到水洗、日曬等偏好的處理法
5. As a 訪客, I want to 依烘焙度篩選咖啡豆（可複選）, so that 我能找到符合口味的焙度
6. As a 訪客, I want to 依風味標籤篩選咖啡豆（可複選）, so that 我能直接找到花香、果酸、堅果或巧克力調性的豆子
7. As a 訪客, I want to 用關鍵字搜尋咖啡豆名稱與風味描述, so that 我能快速找到特定的豆子
8. As a 訪客, I want to 依最新、價格由低到高、價格由高到低排序, so that 我能依自己的方式瀏覽
9. As a 訪客, I want to 在篩選、排序或換頁時不用整頁重新載入, so that 瀏覽過程流暢
10. As a 訪客, I want to 篩選條件反映在網址上, so that 重新整理不會消失，也能把結果分享給朋友
11. As a 訪客, I want to 在篩選結果為空時看到清楚的提示與清除篩選的方式, so that 我不會卡在空白頁面

13. As a 訪客, I want to 在列表上看到每支咖啡豆的最低售價, so that 我能先概略比較價格

16. As a 訪客, I want to 在詳情頁切換規格時看到對應的價格與庫存狀態, so that 我知道每種重量的價錢與是否有貨

## Implementation Decisions

### 架構

- Laravel + MySQL。前台以 Blade 渲染頁面，在需要互動的區塊嵌入 Vue 元件（商品列表的篩選／排序／分頁、規格與研磨方式選擇器、購物車），以 Vite 打包。不做 SPA。
- 介面語言為繁體中文。視覺風格為日系極簡：米白底、大量留白、細襯線標題、低彩度大地色。先完成首頁、咖啡豆詳情、購物車三頁設計稿，再實作畫面；所有頁面共用同一套間距、字級與色彩設定。
- 商品照片使用免費圖庫。

### 領域模型與資料表

- **咖啡豆**：名稱、產地、處理法、烘焙度、風味描述、圖片、是否上架。產地、處理法、烘焙度是咖啡豆的屬性，不是規格。
- **風味標籤**：獨立資料表，與咖啡豆為多對多。
- **規格**：屬於一支咖啡豆，以重量區分，各自有價格與庫存。
- **研磨方式**：固定的一組選項（原豆、手沖、義式等），記錄在購物車項目與訂單項目上，不是規格，不影響價格與庫存（ADR 0001）。
- **購物車／購物車項目**：購物車項目是「規格 × 研磨方式 × 數量」。訪客購物車存在 session；顧客購物車存在資料庫。顧客登入時合併：相同規格與研磨方式的數量相加，超過可購買庫存則調整到上限並提示。
- **訂單／訂單項目**：訂單項目保存下單當下的單價。訂單保存收件資訊、商品小計、運費、總計與付款期限。
- **顧客與店家**是兩張資料表、兩個 Laravel guard、兩套登入頁。一個帳號不會同時是兩者。

### 訂單狀態

```
待付款 ──付款成功──▶ 已付款 ──店家出貨──▶ 已出貨 ──店家完成 或 出貨滿 7 天──▶ 已完成
  │
  ├──付款逾期（30 分鐘）──▶ 已取消
  └──顧客取消──────────────▶ 已取消 ──事後收到付款成功──▶ 付款異常
```

- 狀態轉換集中在同一處定義，不合法的轉換一律拒絕（前台、後台、付款通知都經過同一套規則）。
- 付款逾期與顧客取消走同一條路徑：取消訂單並歸還庫存保留。

### 庫存保留

- 結帳時在同一個資料庫交易中，以列鎖定（`SELECT ... FOR UPDATE`）讀取各規格庫存，全部足夠才扣除並建立訂單；任一規格不足則整筆失敗，並回報是哪個規格。
- 取消訂單時把訂單項目的數量歸還給對應規格。歸還只發生一次。

### 付款（綠界）

- 串接綠界測試環境的信用卡付款。付款模組有清楚的介面，讓測試與將來替換金流時不必改動訂單邏輯。
- 送往綠界的付款期限不超過訂單剩餘的付款時間（實作前須查證綠界信用卡付款可設定的參數）。
- 付款通知：驗證檢查碼；以綠界的交易編號去重，重複通知只處理一次；處理前再檢查一次訂單狀態與付款期限。待付款且未逾期 → 已付款；已取消（或已逾期）→ 付款異常。
- 付款失敗時，訂單在付款期限內維持待付款，顧客可以重新付款。

### 運費

- 只有宅配。運費 NT$100，商品小計達 NT$1,000（含）免運。運費規則集中在一處計算，購物車頁、結帳頁、訂單使用同一個結果。

### Email

- 三封：訂單成立（含付款期限）、付款成功、已出貨。全部透過 Queue 非同步寄出。
- 寄信方式須於實作前查證 Render 免費方案是否允許 SMTP，否則改用有免費額度的寄信服務 HTTP API。

### 排程與 Queue

- 每分鐘：取消已超過付款期限的待付款訂單。
- 每日：把出貨滿 7 天的已出貨訂單改為已完成。
- Render 免費方案沒有 worker 與 cron job，因此網站、`schedule:work` 與 `queue:work` 由 supervisor 在同一個容器中執行（ADR 0002）。休眠期間排程停止，醒來後補處理；付款通知與顧客查看訂單時會再檢查付款期限，補上空窗。

### 圖片

- 透過 Laravel Storage 存取：本機開發存本機磁碟，線上存外部圖片服務（候選 Cloudinary，實作前須查證免費額度）。Render 的檔案系統不會保留。
- 種子資料的商品圖片固定存放在圖片服務上，種子資料只寫入網址。

### 部署

- 網站以 Docker 部署在 Render 免費方案；資料庫為 Aiven 免費 MySQL（ADR 0002）。
- 容器啟動時，若啟用 demo 模式（環境變數控制），重建資料庫並載入種子資料（ADR 0003）。這是刻意的行為，不是 bug。
- 種子資料包含足夠展示篩選效果的咖啡豆（多個產地、處理法、烘焙度、風味標籤）、各自數個規格（含已售完的規格）、公開的顧客與店家測試帳號，以及數筆不同狀態的訂單，讓後台與銷售概況一進去就有內容。
- 所有頁面顯示 demo 提示列：資料會在閒置後重置，以及綠界測試卡號。
- README 註明首次載入約需 1 分鐘；不做保持喚醒的機制。

## Testing Decisions

- **好的測試只驗證外部行為**：從 HTTP 請求進入，檢查回應、資料庫狀態、寄出的信。不直接測試內部類別或方法，重構內部實作時測試不需要修改。
- **唯一的主要切入點是 HTTP 請求層**（Laravel Feature Test，使用 Pest）。外部服務在邊界替換：
  - 綠界：測試自行組出帶正確檢查碼的付款通知，打到回傳網址；檢查碼錯誤的通知必須被拒絕。
  - Email：Mail fake，驗證是否寄出、寄給誰。
  - 圖片上傳：Storage fake。
  - 付款逾期與自動完成：時間旅行後執行排程，再檢查訂單與庫存。
- **測試資料庫使用 MySQL**（本機與 GitHub Actions 相同），因為庫存保留依賴 MySQL 的列鎖定行為。「同時搶最後一包」以連續兩次結帳驗證第二人失敗；鎖定本身由 MySQL 保證。
- **需要測試的業務規則**：
  - 結帳保留庫存、任一規格不足時整筆失敗、最後一包只有一人買到
  - 付款逾期與顧客取消時歸還庫存，且只歸還一次
  - 付款通知：檢查碼驗證、重複通知只處理一次、逾期或已取消後收到付款變成付款異常
  - 訂單狀態只能做合法轉換
  - 訪客購物車登入後的合併規則（相加、超過庫存調整到上限）
  - 同一規格不同研磨方式是不同的購物車項目
  - 運費與免運門檻的計算（含剛好 NT$1,000）
  - 顧客無法進入後台；顧客只能看到自己的訂單
  - 三封 Email 在對應時機透過 Queue 寄出
  - 商品列表的篩選、排序、搜尋結果
- **一支端對端測試**（Playwright）：瀏覽 → 選規格與研磨方式 → 加入購物車 → 登入 → 結帳 → 模擬付款成功通知 → 訂單變成已付款。前端 Vue 元件不另寫單元測試。
- **CI**：GitHub Actions 在每次 push 執行 Feature Test 與端對端測試，README 顯示狀態徽章。
- **Prior art**：repo 目前沒有程式碼，這份規格建立第一批測試。

## Out of Scope

- 退款、退貨、部分取消
- 超商取貨與其他配送方式；綠界物流 API
- 信用卡以外的付款方式
- 優惠券、會員等級、點數
- 收藏清單、商品評論
- 多店家、店家角色權限（店長、客服、倉管）
- 社群登入
- 多語系
- 保持網站喚醒的外部監控
- Vue 元件的單元測試
- 正式上線營運（只做 demo）
